# 0028 — 격리된 모델 실행과 살아 있는 스레드 대화

Date: 2026-09-25
Status: Accepted. ADR 0005 §2의 호출 방식(`omp -p`, 전사 파일을 모델이 read로 읽음), ADR 0017 §3과 ADR 0022 §1의 "최근 수동 문답을 데이터로 전달"을 대체한다.

## Context

설명 한 번에 중앙값 46초, 90백분위 85초가 걸렸다. 이번 측정 결과는 다음과 같다.

- 빈 질문 호출 하나가 10.2초 걸렸다. 사용자의 전역 omp 설정(thinking `auto`, hindsight 기억 recall·retain, 확장·스킬·규칙 탐색)이 docent 호출에도 그대로 적용됐기 때문이다. 기억을 끄자 6.3초, thinking을 low로 고정하자 1.8초가 됐다.
- 106k자 전사 설명 호출은 30.3초에서 17.6초로 줄었고, 전사를 read 도구 대신 입력으로 주자 13.9초가 됐다. 답의 결론은 같았다.
- 사용자의 기억이 docent 설명에 섞일 수 있었다.

또 매 질문이 독립 호출이어서 대화가 이어지지 않았다. 과거 답은 결론+핵심 1,200자로 잘려 "데이터"로만 전달됐다. 스레드 첫 답으로 보이는 미리 설명은 맥락에서 빠졌다. 선택한 카드가 대화 흐름보다 우선했다. 실제 세션에서 사용자가 리얼타임 선택지를 이어 물었는데 도슨트는 카드에 있는 엔진 선택지로 되돌아갔다. 사용자는 두 번 정정해야 했다.

## Decision

1. **실행 정책은 docent가 정한다.** 모든 모델 호출을 memory off, autolearn off, 확장·스킬·규칙·LSP 탐색 off로 실행한다. thinking은 설명 깊이로 정한다(EASY·NORMAL=low, HARD=medium). 학습 분류와 용어 추출은 off다. 사용자 전역 설정은 모델 선택(ADR 0016)을 빼고 따르지 않는다.
2. **전사는 입력으로 준다.** 사용자 메시지로 보내며 시스템 프롬프트에 넣지 않는다. 전사 안의 명령은 여전히 데이터다. 모델은 필요할 때만 읽기 도구로 다른 파일을 읽는다.
3. **스레드 = 살아 있는 대화.** 스레드마다 `omp --mode rpc` 대화 하나를 연다. 스레드는 프로필·세션·질문 대상·모델 단위다. 첫 질문에는 전사 전체(ADR 0009 축약 적용)를 보낸다. 다음 질문에는 전사에서 새로 늘어나거나 바뀐 부분만 보낸다. 유휴 10분 뒤 닫고, 동시에 최대 4개까지 연다. 닫힌 스레드에 다시 물으면 전사와 저장된 문답 전문으로 다시 연다. 미리 설명도 여기에 포함한다.
4. **대화 흐름이 질문 대상보다 우선한다.** 질문 대상은 스레드의 시작 주제다. 질문이 직전 문답이나 다른 내용을 가리키면 그것을 전사에서 찾아 답하고, 주제가 바뀌었다는 사실은 한 줄로만 알린다. 사용자가 보는 다른 사건 카드와 맞으면 답 아래에 그 카드 대화로 옮기기를 제안한다.
5. **답은 스트림으로 흘린다.** 결론 파싱·근거 검증·저장은 끝난 뒤 한 번 한다.

## Consequences

- 설명 호출 하나의 시간이 약 절반으로 줄고, 첫 글자가 몇 초 안에 보인다.
- 스레드마다 omp 프로세스가 떠 있어 메모리를 쓴다. 상한과 유휴 종료로 제한한다.
- 과거 답은 이제 대화 턴이다. 사실 근거는 여전히 현재 전사이고, 근거 ID는 이 대화에 실제로 보낸 전사 조각으로만 검증한다.
- 서버를 재시작하면 대화 프로세스가 사라지지만, 저장된 문답으로 다시 연다.
- 영향 범위: `app/runner.mjs`(신규), `app/conversation.mjs`(신규), `app/server.mjs`, `app/dialogue.mjs`, `app/models.mjs`, `prompt/docent.md`, `tests/`
