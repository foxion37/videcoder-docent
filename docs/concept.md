# 개념

## 문제

바이브코더는 메인 에이전트(Claude Code, Codex, omp 등)에게 일을 시키지만, 결과로 나온 코드·diff·에러 메시지를 스스로 읽기 어렵다. 그래서:

- 지금 에이전트가 뭘 했는지 모른 채 "됐어요?"만 묻는다.
- 에러가 나면 원인을 모르고 같은 지시를 반복한다.
- 다음에 뭘 요청해야 할지 몰라 세션이 멈춘다.

메인 에이전트에게 설명을 시키면 작업 흐름이 끊기고, 답변이 개발자 어투로 나온다.

## 해법

작업 세션 옆에 붙는 **도슨트** 웹앱. 미술관 도슨트처럼 코드를 만지지 않고 설명한다. 작업 흐름에서 궁금한 항목을 고르고 그 맥락에서 자유롭게 이어 묻는다. 필요할 때 원문을 열어 확인하고, 이해 상태와 남은 의문은 "배운 내용 다시보기"에서 돌아본다. 지원 브라우저에서는 작업창 위 PiP 작은 창으로 같은 대화를 이어 간다 (ADR 0017).

## 사용자

- 1차: 비개발자 바이브코더. 터미널은 열 수 있지만 코드는 못 읽는다.
- 2차: 초보 개발자. 코드는 읽지만 "왜 이렇게 했는지"를 모른다.

## 핵심 동작

| 입력 | 도슨트 출력 |
| --- | --- |
| "지금 뭐 한 거야?" | 최근 변경을 파일 단위가 아니라 "무엇이 달라졌는지" 단위로 요약 |
| "이 에러 뭐야?" | 증상, 확인된 원인, 추측을 구분한 설명 |
| "이거 왜 이렇게 했어?" | 세션 기록에서 근거 찾아 설명. 근거 없으면 "기록에 없음"이라고 말함 |
| "다음에 뭐 시켜야 해?" | 현재 상태 기준 실제 남은 일. 보낼 문장은 사용자가 원할 때만 |
| "이 파일 뭐 하는 거야?" | 파일 역할을 비유·예시로 설명 |

## 지켜야 할 것

- 코드를 수정·생성·실행하지 않는다. 담당 에이전트에게 보낼 요청 문장은 사용자가 요청할 때만 쓴다.
- 모르는 건 모른다고 한다. 추측이면 추측이라고 표시한다.
- 답은 한 줄 결론 / 질문에 맞는 핵심 설명 / 필요할 때 펼쳐 보는 "더 자세히" 순서다. 고정 양식을 채우지 않고 질문 모양(뜻, 비교, 이유, 단계)에 맞춘다 (ADR 0017).
- "그거", "두 번째" 같은 이어 묻기는 사용자가 고른 질문 대상과 최근 문답으로 해석한다. 사실은 현재 전사로 확인한다.
- 용어는 처음 나올 때 한 줄로 푼다. 예: "린트(코드 맞춤법 검사)".
- 같은 개념·의문을 다시 물으면 미해결 신호로 보고 설명 전략을 바꾼다. 다른 사건·자동 질문·요청 재전송은 구분한다.
- 이해 대상과 기술 분야를 따로 분류하고, 설명한 적 있다는 이유로 이해했다고 판단하지 않는다.
- 현재 작업의 근거가 과거 설명보다 우선한다. 확인된 근거만 웹앱 원문 패널로 연결한다.

## 입력 소스

omp·Claude Code·Codex CLI·Gemini CLI·pi 세션 전사가 작업 사실의 1차 근거다. 사용자별 학습 기억은 설명 방식과 미해결 지점의 참고 자료이며 현재 사실을 대신하지 않는다. 제공된 원문을 벗어난 상황은 추측으로 구분한다. 자세한 흐름은 @docs/architecture.md.
